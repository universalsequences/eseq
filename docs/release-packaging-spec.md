# Release Packaging — Specification

Status: rev 1, 2026-08-21. Scope: turning the workspace build into an
artifact a person installs. Companion to
`crates/sequencer/docs/embedded-dgen-toolchain-v0.1-spec.md` (which owns
signing, notarization, and the hermetic compile proof) and
`docs/content-tiers-spec.md` (which owns the factory/user/package layout).

---

## 1. Why this document exists

The toolchain spec answers *"can a runtime-generated dylib compile and load
inside a signed bundle."* That is the risky question and it is well covered.
It does not answer *"what does a person download."*

Neither spec currently mentions a DMG, a bundle identifier, an app icon, a
version string, or an update mechanism. `AppPaths::Release` exists as a shape
but nothing constructs it. This document fills that gap and sequences it into
three rungs, so the first testable artifact does not have to wait on an Apple
Developer account or a second machine.

### 1.1 The measured starting point

The diffuse half of this problem is already solved. A scan of non-test code
in `crates/sequencer/src` finds **zero** relative-path filesystem accesses:
every read and write resolves through `AppPaths`. What remains is
concentrated in a handful of named places, listed in §4.

---

## 2. The three rungs

| Rung | Artifact | Needs | Proves |
|---|---|---|---|
| **R1** | Unsigned/ad-hoc `.app` in a DMG, built locally | Nothing external | The bundle layout, the Release path arm, first-run on a machine that is not the dev checkout |
| **R2** | Same artifact, built in CI on every `main` commit | GitHub Actions | Reproducibility off the dev machine; a tip channel to hand out |
| **R3** | Developer ID signed, notarized, stapled, Sparkle updates | Apple Developer Program, a clean Mac | Gatekeeper, hardened runtime, library validation against generated dylibs |

**R1 is the deliverable for developer friends.** They will run
`xattr -dr com.apple.quarantine /Applications/ESeq.app` without complaint.

### 2.1 Why R1 is genuinely easier for this app, not merely cheaper

ESeq compiles and loads dylibs at runtime. Under an unsigned or ad-hoc build
there is no hardened runtime, so there is no library-validation constraint on
those dylibs and the `com.apple.security.cs.disable-library-validation`
question does not arise. R1 therefore removes the single most uncertain
element of R3 rather than deferring it.

### 2.2 What R1 deliberately does not prove

The toolchain spec is explicit that notarization passing is not evidence that
runtime-generated dylibs load, and the converse holds too: **R1 passing is not
evidence that R3 will pass.** R1's value is real testers and real bug reports
on the *content and product*, in parallel with signing work — not a shortcut
through it. The release acceptance matrix in the toolchain spec (§ Release
acceptance) remains the exit criterion for R3 and is not weakened by R1.

### 2.3 Prior art: Ghostty

Ghostty is the reference for the eventual shape. Two channels — `tip`, built
from every passing commit on `main` and indexed by commit hash, and a tagged
stable channel — both signed with Developer ID, packaged with `create-dmg`,
notarized via `xcrun notarytool`, and stapled. Sparkle drives updates; the
appcast feeds are generated by scripts under `dist/macos/` that pull EdDSA
signatures from Sparkle's `sign_update` and prune to the last 15 builds. All
of it runs in GitHub Actions.

Two adaptations for ESeq:

1. **Ghostty's tip channel is signed and notarized too.** Copying their model
   directly front-loads the Developer ID, the notarization pipeline, and
   Sparkle before the first tester. R1 is a rung *below* Ghostty's floor.
2. **This repository has no CI at all** (no `.github/workflows`). Their model
   is entirely Actions-driven, so R2 is net-new infrastructure, not a port.

## 3. Product shell decisions

These are unmade today and cheap to make now. Each is load-bearing for R1.

### 3.1 Bundle identifier — decide once, migrate never

`AppPaths::Release` routes user data to
`~/Library/Application Support/<bundle-id>/` and generated artifacts to
`~/Library/Caches/<bundle-id>/`. Changing the identifier after any tester has
saved a project orphans their library and requires a migration path.

**Recommendation: `com.universalsequences.eseq`.** Matches the existing GitHub
owner, is unambiguous, and needs no domain purchase. `dev.eseq.*` reads better
but assumes a domain that is not owned.

### 3.2 Names — three exist, one must win

| Where | Current |
|---|---|
| Cargo package | `sequencer` |
| UI binary | `metal_seq` (`crates/sequencer/src/ui/main.rs`) |
| CLI binary | `eseq` |
| Toolchain spec bundle | `ESeq.app` |

**Recommendation:** the product is **ESeq**; the bundle is `ESeq.app`; the
`CFBundleExecutable` stays `metal_seq` (renaming the Cargo bin target touches
test invocations, probes, and docs for no user-visible gain). `CFBundleName`
= `ESeq`, `CFBundleDisplayName` = `ESeq`.

The `eseq` CLI ships inside `Contents/MacOS/` and is reachable by path. A
`PATH` install or symlink is out of scope for R1.

### 3.3 Version

`CFBundleShortVersionString` from the crate version (`0.1.0`),
`CFBundleVersion` from a monotonic build number. For R1, `CFBundleVersion` may
be the short git hash; R2 replaces it with a CI run number, since Sparkle in
R3 requires `CFBundleVersion` to be monotonically increasing.

### 3.4 Icon

Required for R1 — an unbranded generic icon is the single loudest "this is not
a real app" signal to a first tester. `Contents/Resources/AppIcon.icns`,
`CFBundleIconFile` = `AppIcon`. Source artwork lives in `dist/macos/`.

### 3.5 Minimum system version

`LSMinimumSystemVersion` = `11.0`, matching `minimum_macos` in the staged
toolchain's `VERSION.json`. Apple Silicon only (`arm64`), per the toolchain
spec's primary platform.

## 4. R1: what the code must change

### 4.1 Nothing constructs the Release arm

`app_paths::init_dev()` and the lazy `app_paths()` fallback both build
`AppPaths::Dev` from `crate::paths::workspace_root()`, which is
`env!("CARGO_MANIFEST_DIR")` — a compile-time absolute path into the build
machine's checkout. There is no `init_release()`.

Add one. `AppPaths::release(contents_macos, contents_resources,
application_support, caches, user_lisp_root)` already exists and is already
consumed correctly by every accessor; only the constructor and the roots are
missing.

### 4.2 Arm selection

**Detect at runtime from `std::env::current_exe()`:** if the executable sits
in `…/Something.app/Contents/MacOS/`, take the Release arm with
`contents_macos` and `contents_resources` derived from that ancestor;
otherwise take Dev. One binary, both behaviors, and `cargo run` from the
workspace is unaffected.

A build-time feature flag is the alternative and is rejected: it makes the
bundled binary untestable from the workspace, which is exactly the debugging
loop R1 needs to stay fast.

Per the toolchain spec's Development Mode rules, the Release arm **ignores**
`ESEQ_DGEN_TOOLCHAIN_ROOT`. `SEQUENCER_ROOT` and `ESEQLISP_ROOT` should be
ignored on the Release arm for the same reason.

### 4.3 The startup sequence

`crates/sequencer/src/ui/main.rs`:

```
105  sequencer::paths::enter_sequencer_dir()?;      // dev-only, must be skipped
106  sequencer::app_paths::init_dev()?;             // must branch
108  app_paths.ensure_user_tier()?;                 // correct as-is
109  reconcile_app_package_samples(app_paths)       // correct as-is
```

`enter_sequencer_dir()` chdirs into the crate directory. In a bundle its
lookup (`find_package_dir`: `SEQUENCER_ROOT` → cwd → ancestors of
`current_exe()` containing `crates/` → `CARGO_MANIFEST_DIR`) fails every
branch and returns `Err("sequencer crate directory not found")`, which
propagates out of `main` — **the bundled app exits before opening a window.**
That is the first symptom to expect, and the first thing R1 fixes.

`ensure_user_tier()` already creates the full mutable shape and is safe on
every launch, so first-run on a clean account needs no new code.

### 4.4 Bundle layout

Per `docs/content-tiers-spec.md` §3 (`Resources/  <content/ copied verbatim>`)
and the accessors in `app_paths`:

```
ESeq.app/Contents/
  Info.plist
  MacOS/
    metal_seq          <- CFBundleExecutable
    eseq               <- CLI
    DGenLisp           <- from crates/sequencer/tools/DGenLisp
  Resources/
    AppIcon.icns
    dgen-toolchain/    <- from crates/sequencer/tools/dgen-toolchain (~140 MB)
    core/  ui/  defmacros/  effects/  instruments/  midi-fx/
    presets/  kits/  processes/  scripts/  impulses/  filter-tables/
                       <- content/ copied verbatim
```

**Conflict to resolve:** the toolchain spec's Bundle Layout section shows
`Resources/runtime/eseqlisp/init.lisp` and `Resources/factory/…`. The code
disagrees — `factory_root()` returns `contents_resources` directly, so
`core_dir()` is `Resources/core`. `content-tiers-spec.md` is rev 2 and newer;
the code follows it. **The toolchain spec's layout section is stale and must
be corrected to match**, or the accessors changed. Do not ship the ambiguity.

### 4.5 The staged toolchain is gitignored

`crates/sequencer/tools/dgen-toolchain` is ~140 MB, produced by
`./rebuild_dgenlisp_tool.sh`, and not in git. The dist script must fail loudly
with that command in the error when the stage is absent, rather than
producing a bundle that cannot compile anything. `VERSION.json` from the stage
should be recorded in the build log.

### 4.6 Dev-only paths that must degrade, not crash

`poll_editable_shader_overrides` reads
`env!("CARGO_MANIFEST_DIR")/shaders/button_surface.metal` every frame from
`crates/sequencer/src/ui/event_loop.rs:311`. It already returns `false` and
logs once when the file is missing, so a bundle is *functionally* fine — but
it is a per-frame `fs::metadata` on a path that can never exist. Gate it off
on the Release arm.

This is the class of issue R1 exists to surface. There may be others; the
acceptance below is written to catch them.

### 4.7 The dist script

`dist/macos/build.sh` — plain shell, no Xcode project:

1. `cargo build --release` for `metal_seq` and `eseq`.
2. Verify the staged toolchain exists; abort with the rebuild command if not.
3. Assemble the tree in §4.4.
4. Generate `Info.plist` with the keys from §3.
5. Ad-hoc sign (`codesign -s -`) so the app is launchable without a Developer
   ID. R3 replaces this step; nothing else in the script changes.
6. Produce `ESeq-<version>-<hash>.dmg` via `hdiutil` (or `create-dmg` if the
   window layout is wanted — Ghostty uses it, and R3 will).

Output to `dist/out/`, gitignored.

## 5. R1 acceptance

- The DMG mounts; dragging to `/Applications` and launching (after quarantine
  removal) opens the app with **no dev checkout present on the machine**.
  Testing on the build machine is insufficient — the Dev arm's `current_exe`
  ancestor walk can find a sibling checkout and mask the failure.
- A clean user account produces a populated `~/Library/Application Support/
  <bundle-id>/` and `~/.eseq.d/`, and no write is attempted inside the bundle.
- Factory instruments and effects load; a new DGen instrument compiles,
  auditions, saves, and survives restart — using only the bundled toolchain.
- The app is moved to another directory and still launches.
- `strings` on the shipped binaries reveals no path into the build machine's
  home directory or checkout.
- A tester who has never seen the repo can install and make sound from the
  README instructions alone.

## 6. R2 sketch (not scoped here)

GitHub Actions on `macos-14` or newer: run the dist script, upload the DMG as
a release asset on a rolling `tip` tag. Requires the staged toolchain to be
either rebuilt in CI or fetched from a release asset — it is too large to
commit. Decide that before writing the workflow.

## 7. R3

Owned by `crates/sequencer/docs/embedded-dgen-toolchain-v0.1-spec.md` Phase 5
and bead `eseq-toolchain.3`. Sparkle, the appcast, and the two channels are
additive to that and are not yet specced; do so when R2 exists.

## 8. Open questions

1. **Bundle identifier** (§3.1) — recommendation given; needs ratification
   before any tester saves a project.
2. **Icon artwork** — who makes it. Blocks R1 shipping, not R1 code.
3. **Toolchain-spec layout conflict** (§4.4) — must be resolved in one
   direction as part of R1.
4. **Toolchain distribution for CI** (§6) — rebuild or fetch.
5. **Crash reporting.** `sequencer::crash::install()` exists; whether a
   tester's crash log reaches you is unaddressed. Out of scope for R1, but the
   first thing you will want once friends are running it.
