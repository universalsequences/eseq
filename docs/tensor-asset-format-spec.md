# Tensor Asset Format — rev 2

Status: PROPOSED (nothing implemented; this spec formalizes the de-facto
format and adds the one mechanism that removes hardcoded UI label lists).

## Motivation

Tensor JSON assets are now first-class in the patcher: the asset sidebar
lists them, OS drops import them into drafts, and a drop creates a
file-backed `(tensor @shape […] @file "…")` node. Users will author their
own assets, so the format needs to be written down. Separately, the
factory wavetable and triton UIs hardcode duplicate copies of the set
names that already live in their banks' JSON (`wt-set-options` in
`content/instruments/core/wavetable/ui.lisp:50`, the parallel lists in
`content/instruments/core/triton/ui.lisp:27`) because Lisp UI has no way
to read asset metadata. Blessing the metadata keys and exposing them to
Lisp lets any patch mix and match asset files and auto-generate its
selector dropdowns from whatever bank is plugged in.

## 1. The contract (required keys)

A tensor asset is a UTF-8 JSON object with two required keys:

```json
{
  "shape": [512, 448],
  "data": [0.0, 0.012, …]
}
```

- `shape` — non-empty array of positive integers. This is the machine
  validity check everywhere: the patcher sidebar/drop path deserializes
  only `{ shape }` (`crates/eseqlisp/src/widget_render/patcher/assets.rs`,
  `read_tensor_asset_shape`), and the generated node's `@shape` must
  multiply out to `data.len()`.
- `data` — flat array of finite numbers, length = product of `shape`,
  laid out row-major in shape order. For a 2-D `[frame_len, wave_count]`
  bank this is wave-major: `index = wave * frame_len + sample`.

Any other key is ignored by the compile path. Unknown keys MUST be
tolerated by every consumer (they already are — everything deserializes
selectively).

A bare top-level JSON array (no object wrapper) is accepted by the
wavetable-viewer widget as legacy input but is NOT a valid asset: it has
no `shape`, so the patcher sidebar, drop import, and this spec all
exclude it. New files always use the object form.

## 2. Standard metadata keys (optional)

These keys are already emitted by `gen_bank.py` / `extract_bank.py` and
`basic-shapes.json`; this spec blesses them so UIs can rely on them.

| key             | type        | meaning |
|-----------------|-------------|---------|
| `kind`          | string      | What the tensor is, e.g. `"wavetable-bank"`, `"impulse"`, `"filter-table"`. Lets inspectors/widgets pick a rendering. Absent = generic tensor. |
| `layout`        | string      | Human-readable index formula, documentation only. |
| `source`        | string      | Provenance / license note, documentation only. |
| `waves_per_set` | integer ≥ 1 | Wavetable banks: groups the wave axis into sets. `wave_count % waves_per_set` should be 0. |
| `sets`          | [string]    | Set display names; length = `wave_count / waves_per_set`. |
| `wave_names`    | [string]    | Per-wave display names; length = total wave count. |

Wavetable-bank conventions (`kind: "wavetable-bank"`): `shape` is
`[frame_len, wave_count]`, wave-major data. The factory banks flatten
set structure into the wave axis (`[512, 448]` = 28 sets × 16 waves);
set structure lives only in `waves_per_set`/`sets`, never in a third
dimension, so the dgen `@shape` stays 2-D.

Validation stance: metadata is advisory. A length mismatch (e.g. `sets`
shorter than the set count) must never fail a compile or hide the asset
from the sidebar; consumers clamp/truncate and may warn. Only §1 keys
gate validity.

## 3. New mechanism: `asset-metadata` Lisp native

The single missing piece. A host-side native (registered in
`crates/eseqlisp/src/editor/natives.rs`) that parses an asset's header
and returns it as a dict — never the `data` floats:

```lisp
(asset-metadata "instruments/core/wavetable/waves/bank.json")
;; => (dict :shape '(512 448)
;;          :kind "wavetable-bank"        ; when present
;;          :wave-count 448               ; derived: product of shape[1..]
;;          :waves-per-set 16
;;          :set-count 28                 ; derived
;;          :sets '("Basic Shapes" "Harmonics" …)
;;          :wave-names Nil               ; absent key => Nil
;;          :source "procedurally generated by gen_bank.py"
;;          :layout "wave-major: …")
;; => Nil when the file is missing or fails the §1 contract
```

- **Resolution**: the same precedence as dgen `@file` (draft dir →
  user assets → factory), reusing the resolver documented at
  `crates/sequencer/src/lisp_host/dgen/dylib_cache.rs:1223` /
  `hot_reload::resolve_content_relative_asset`, so the string a UI
  passes is the same string the DSP's `@file` uses. No absolute paths.
- **Caching**: cache parsed headers keyed by resolved path + mtime,
  mirroring the `wavetable_viewer` bank cache, so calling this inside a
  reactive UI body is cheap. Returned dicts are plain values; the UI
  subtree re-runs only when its own deps change, and a stale cache after
  an external file edit heals on the next mtime check.
- **Derived fields**: `:wave-count` = product of all dims after the
  first, `:set-count` = `wave-count / waves-per-set` (floor, min 1),
  computed host-side so Lisp never re-implements the layout math.

Deliberately NOT a generic `parse-json` native: a schema-shaped
accessor keeps path resolution, caching, and the derived fields in one
place, and avoids handing UIs a footgun that reads 17 KB float arrays
into Lisp values.

## 4. UI auto-generation

With §3, the hardcoded lists die:

```lisp
;; wavetable ui.lisp — before
(def wt-set-options ()
  '("Basic Shapes" "Harmonics" …))          ; 28 dual-maintained strings

;; after
(def wt-set-options ()
  (let ((meta (asset-metadata (wt-bank-file))))
    (if meta (get meta :sets) '("Bank"))))
```

Same change in triton's ui.lisp. The `waves-per-set` prop passed to the
`wavetable-viewer` widget likewise comes from metadata instead of the
literal `16`, and the widget's own default should read `waves_per_set`
from the JSON when the prop is absent (small change in
`wavetable_viewer.rs`, which already parses the file).

Mix-and-match falls out: an instrument that exposes its bank path (a
`@file` on its tensor node, or a fork that swaps `wt-bank-file`) gets a
dropdown sized and labeled by whatever file is referenced — a 4-wave
`basic-shapes.json` yields one set with 4 waves, a 448-wave bank yields
28 sets — with no UI edits.

## 5. Generated patcher UI: `@options` (the key use case)

Patcher-built instruments never get a hand-written ui.lisp: their UI is
auto-generated from the param manifest. The pipeline is
`(param name @group amp @env amp-env @role attack …)` → dgenlisp
compiler emits manifest JSON → `dgen_manifest.rs` parses the fixed
fields into `DGenParam` (name/group/env/role/min/max/unit/hidden) →
`content/ui/effects/param-grid.lisp` builds grouped sections and env
panels from those dicts. A user who drops `basic-shapes.json` into a
draft and adds a set-select param should get a labeled dropdown for
free, exactly like `@group` gives them sections for free.

One new param attribute closes the loop: `@options` declares the param
a labeled discrete choice. It takes one of two label sources:

```lisp
;; inline literal labels (enum-ish params: modes, algorithms, types)
(param mode @options ["lowpass" "highpass" "bandpass" "notch"])

;; a tensor variable reference — labels come from the asset backing it
(def bank (tensor @shape [512 4] @file "waves/basic-shapes.json"))
(param table @options bank @default 0)
```

Both forms share every downstream behavior — derived integer-stepped
domain `0..(len labels - 1)` (so `@min`/`@max` are omitted), dropdown
rendering in the generated UI, label display in p-locks. They differ
only in when labels resolve: inline labels are baked into the manifest
at compile time (`"options": {"labels": […]}`); the tensor form stays
host-resolved so labels track bank swaps and `tensor-param` pushes.
The attribute is deliberately source-agnostic — a future third label
source (e.g. a tuning file) adds a manifest variant, not new surface.
Bracket arrays follow `@shape`/`@data` conventions (no commas), and
patcher node text already lexes bracket attribute arrays correctly, so
the inline form needs no patcher work at all.

The tensor form takes a **variable reference**, not a path (the
`@sidechain sc` precedent — attributes that name a binding are already
idiomatic dgenlisp):

- **Why a reference, not a path**: a path string would spell the file
  twice (once on the tensor, once on the param); swap the bank and
  forget the param and the audio and labels silently come from
  different files — the drift class this spec exists to kill. The
  reference keeps one source of truth, and compile-errors early and
  clearly if it names a tensor with no file contents (`@data` or
  zero-filled).
- **Semantics**: the param's option labels come from the referenced
  tensor's asset metadata. Default key policy: `sets` if present,
  else `wave_names`, else numbered `1..N` — so bare `@options bank`
  covers the common case; `@options-key wave-names` selects another
  list key only when deviating. The param's domain is derived:
  `0..(len labels - 1)`, integer-stepped, so option params omit
  `@min`/`@max` entirely (authored values are ignored with a compile
  warning). A bank swap re-derives labels and domain on the next
  compile with no UI edit — this is what makes asset mix-and-match
  real for patcher instruments.
- **`tensor-param`**: `@options wave` on a host-writable
  `tensor-param` tracks the *currently pushed* contents — the
  manifest carries the tensor's name, so the host can re-derive
  labels when it pushes a new bank at runtime. This falls out of the
  reference design and is impossible with a static path string.
- **Manifest plumbing**: verified against the vendored compiler
  (2026-08-31): an unknown attribute on a `(param …)` is silently
  ACCEPTED but DROPPED from the emitted manifest, so this needs a
  dgenlisp change + revendor, the same reason `@group` did (`@group`
  is not even passthrough: it prefixes the manifest param name, e.g.
  `amp.gain`). Because `@options` resolves a binding (tensor form)
  and derives domains, it is a small real compiler feature, not
  blind passthrough. The manifest emits one of two variants:
  `"options": {"labels": ["lowpass", …]}` for the inline form, or
  `"options": {"tensor": "bank", "file": "waves/basic-shapes.json",
  "key": "sets"}` with `file` resolved from the binding's `@file`
  (or `@default-file`). A generic inert-attr passthrough map is
  still worth adding in the same compiler rev for future UI-only
  hints. Host side: an `Option<DGenParamOptions>` enum on
  `DGenParam` (Labels(Vec<String>) | Asset{tensor, file, key}),
  surfaced into the param dicts Lisp sees as `:options`. Silent tolerance means back-compat
  is safe: sources carrying `@options` still compile on older
  vendored binaries, just without the dropdown.
- **Rendering**: `param-grid.lisp` checks `:options` before
  falling back to a knob; when present it resolves labels via
  `(asset-metadata …)` (§3) — same resolution the DSP's `@file` used,
  so labels can't come from a different file than the audio — and
  renders the existing micro-option/dropdown lego with those labels.
  Missing file or key degrades to a plain integer knob over the
  authored range, never a broken UI.
- **Patcher surface — the graph is the reference**: patcher users
  never type a symbol, and don't need to. The emitter already claims
  a deduped binding per node (`binding_base_for_node` +
  `claim_unique` in `generate.rs`; "the source is only a build
  artifact"). The link is expressed as a **cable from the tensor
  node into the param node** — params have no inlets today, so a
  cable into one is unambiguous — and writeback resolves the cable's
  source node to its claimed binding and writes `@options <binding>`
  into the emitted `(param …)` form. One new emission rule: an
  options-referenced tensor is forced into a `def` even at fan-out 1
  (the same materialization trick as the bare-top-level rule for
  modulatable params). Importing hand-written source with
  `@options bank` renders back as that cable, so the text and graph
  surfaces project onto the same form.
- **Patcher sugar (follow-up)**: the patcher could additionally
  infer the cable when a param node feeds the set-select inlet of a
  wavetable-read whose tensor inlet is file-backed, the way
  `cutoff~`/mod wiring infers `@mod true` today — likely the main
  path for drop-asset → add-param → dropdown. The attribute is the
  contract; the cable is the patcher surface; inference is
  convenience.

## 6. Migration

1. Implement `asset-metadata` (+ tests: object form, bare-array
   rejection, missing file, truncated `sets` clamp, draft/user/factory
   precedence).
2. `gen_bank.py` / `extract_bank.py`: add `"kind": "wavetable-bank"`
   and (optional) `wave_names`; regenerate banks. Generators are the
   source of truth; the JSON keys they already emit do not change.
3. Wavetable + triton ui.lisp: replace hardcoded set lists and
   `waves-per-set` literals with metadata reads. Delete the duplicate
   lists.
4. `wavetable-viewer`: default `waves-per-set` from the file's
   metadata when the prop is absent.
5. `@options` (§5): dgenlisp compiler feature (binding resolution +
   manifest emission) + revendor,
   `DGenParam` fields, param-grid dropdown rendering, domain
   derivation. This is the patcher-instrument payoff and can land
   after 1–4 (hand-written UIs need only §3).
6. Patcher inference sugar for `@options` (§5, follow-up).
7. Document the format for asset authors: `content/assets/README.md`
   summarizing §1–§2 with a copyable minimal example.

Back-compat: all existing assets already satisfy §1–§2; no file changes
are required for anything to keep working. Step 2 is additive.

## 7. Open questions

1. **Patcher asset inspector** — a read-only modal from the sidebar
   showing §2 metadata plus a wavetable-viewer plot (see the
   inspector discussion; complementary, not required by this spec).
2. **Hand-written dsp.lisp param ranges** — §5 derives domains for
   `@options` params; wavetable/triton's own set params could
   adopt the same attribute once it exists, retiring their baked
   `@max` values too.
3. **`wave_names` in dropdowns** — the wave knob is continuous
   (morphing), so per-wave names likely surface only in the inspector
   and viewer hover, not as a discrete dropdown; `@options-key
   wave-names` covers the discrete case when someone wants it.
4. **Sets as a third dimension** — rejected for now: dgen `@shape`
   consumers and the viewer all assume 2-D banks; `waves_per_set`
   metadata carries the grouping losslessly.
5. **`@options` p-lock display** — option params should print
   their labels in step p-locks like builtin enum params; needs the
   label list to reach the p-lock text-value path (cf. the builtin-fx
   enum display precedent).
