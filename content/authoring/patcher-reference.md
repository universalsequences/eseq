Read this before you explain or change an instrument or effect the user has
open in the patch editor (the "patcher"). DGenLisp rules themselves are in the
`instrument` and `effect` guides. This one covers how the patch relates to the
code, what the context tells you about it, and how to get from a box to its
source.

## The patch and the code

An instrument or effect is one `dsp.lisp` file. It opens on one of two
surfaces, and the toolbar's `Patch | Code` toggle switches between them:

- **Code**: a writable DGenLisp text buffer, `*instrument-code:<name>*` or
  `*effect-code:<name>*`. Typing does not compile. Eval (`C-c C-c` or the Eval
  button) compiles it, and Save writes the buffer text to `dsp.lisp` exactly as
  it is, comments included.
- **Patch**: boxes and cables, in `*instrument-patcher:<name>*` or
  `*effect-patcher:<name>*`. That buffer draws widgets and has no text. Each
  edit regenerates the source from the boxes and compiles a preview.

On the Patch surface the patch model is the source of truth, and `dsp.lisp`
is generated from it. The file starts with
`;; generated by the patch editor — edit via the patcher or eject to code`,
holds one top-level form per box, and loses any hand-written `;` comments.

The patch editor opens only for patch-authored items. An item is
patch-authored when its `dsp.layout.json` sidecar says `"authored": true` and
the patcher can draw all of its source. Everything else (agent-written or
hand-written code) opens on the Code surface. New drafts start on Patch.

### The layout sidecar

`dsp.layout.json` sits next to `dsp.lisp` and holds more than positions:

- `root.nodes`: each box's `x`/`y` (and `width`/`height` when resized), keyed
  by box id.
- `root.cables`: the routing of cables drawn as segmented lines, keyed
  `from:outlet->to:inlet` (0-based), for example `mix-0:0->Left:0`.
- `root.inputPresentation`: inlets drawn inline instead of with a cable.
- `macros.<name>`: the same three maps for each subpatch.
- `graph` (version 3): the whole patch model, with every box, cable and
  comment box. For an authored item, the patcher loads from this, not from
  `dsp.lisp`.

Because the patcher loads `graph` and not the file, never write `dsp.lisp` on
disk for a patch-authored item. The patcher would not show your edit, and the
next Save would regenerate the file from the boxes and wipe it. Make code
changes through the code buffer (see "Changing a patch").

## Reading boxes

Each box is one DGenLisp form, written as the form without its parentheses.
Max users will know the style:

- `phasor 2` is `(phasor 2)`. A number in a box is baked into the call.
- The first inlet is implied: `* 0.5` is `(* <cable> 0.5)`. A `?` marks a
  cabled inlet that has to be spelled out, so `- ?` is `(- <cable> <cable>)`.
- A bare param name in a box (`mix ? ? amount`) reads the param inline, with
  no cable. `cutoff~` reads the host-modulated value `(mod cutoff)`.
- `param cutoff @default 900 @min 40 @max 12000` is a `(param …)` form.
  `in 2 @name pitch` and `out 1 @name left` are the host inputs and outputs.
- `history` is `(make-history …)`. The cable into it is the `write-history`.
  That cable is drawn dashed (a feedback cable), and the box's outlet reads
  last sample's value.
- A box whose text starts with `;` is a comment. Comments live only in the
  sidecar and never reach `dsp.lisp`.
- `mod1`..`mod4` (the `@modulator` inputs) have no boxes. The generator
  writes them for you whenever a param is `@mod true`.

Cables are references. A cable from box `lfo` into inlet 2 of a `*` box means
the `*` form's second argument is `lfo`. Inlets count from 1 in what the user
sees, and each one is an argument position of the call.

### Box ids and the code

A box's id is the name its form has in the source:

| Source form | Box id |
| --- | --- |
| `(def lfo (phasor 2))` | `lfo` |
| `(param cutoff …)` or `(def amt (param mix …))` | `cutoff`, `amt` |
| `(def pitch (in 2 @name pitch))`, `(out x 1 @name left)` | `pitch`, `left` (the `@name`) |
| `(make-history fb)` | `fb` |
| an unnamed call nested in a bigger form, `(* (sin x) 2)` | `sin#0` (operator + `#` + count) |
| a box the user made since opening | `created-7` |

Generated source names every box. Ids that are valid names are kept as they
are. In the others, `#` and `~` become `-` and operators become words, so
`*#0` is written as `mul-0` and `+#1` as `add-1`. A `created-N` box is named
after its operator, for example `phasor-2`. Once the patch has been saved and
reopened, every id is the name of its `def`.

## Subpatches

A subpatch is a local `(defmacro name (a b) …)`, and each box that calls it
is an instance. Inside the macro's view, `in K @name a` boxes are its
parameters in channel order. Its `out` boxes are what it returns, as a
`(tuple …)` when there are several, and a caller destructures that:
`(def (lo hi) (split input 800))` gives the instance two outlets. Box ids
inside a macro view belong to that `defmacro` body, not to the root.

- Encapsulate (Cmd+E, or right-click > Encapsulate) turns the selection into a
  new macro called `sub1`. The user can rename it by double-clicking.
- Library macros come from `content/defmacros/` and are imported with
  `(use-defmacro name)`. Every patch that imports one shares it. Right-click >
  "Fork into Patch" gives this patch its own copy.
- To find out which macro view is open, call `view_state_live` on the patcher
  buffer and read `editor.open-macro`.

## Shapes, tensor cables and probes

The compiler reports each top-level binding's shape, and the patcher maps that
back to boxes. A cable carries the shape of the box it comes from. The context
spells a shape as kind, dims and lanes:

- `signal scalar`: one value per sample. `constant scalar`: a fixed number.
- `signal-tensor [8], 8 lanes`: 8 signals side by side, like a Max `mc` cable,
  for example `(phasor (* (iota 8) 110))`. `[8 1]` is a different shape from
  `[8]`, and combining the two broadcasts to `[8 8]` (64 lanes). Most tensor
  bugs come from that.
- `tensor …`: data that does not change per sample. `tensor-history`: a
  history holding a tensor. `tuple`: a box with several outlets.
- `shape unknown`: the latest compile has not reached it, or the box is
  inside a macro view. Shapes are only reported for the root view.

Tensor cables are drawn thicker, in two alternating colours. When a compile
fails, the box whose form failed gets a red border and the compiler's message.

A probe is `(probe x @id "p1" @view number|scope|spectrogram)`, typed as
`number~`, `scope~` or `spectrogram~`, or added from right-click >
Insert Probe. It passes its input through unchanged and shows the live value,
waveform or spectrum of the signal at that point on the track's playing
instance. It does not change the sound.

## What the context gives you

When the user is in the editor, the `<app-context>` block describes its tile:

```
- *effect-patcher:crusher* (…)
  the patch (boxes and cables over the same DGenLisp) of effect crusher (/…/crusher/dsp.lisp), in slot 1 of track 2
  compiled: what plays is what is on screen
  not saved
  selected: box lfo `phasor rate` (signal scalar); box mul-0 `* ?` (signal-tensor [8], 8 lanes)
  selected cable: phasor · outlet 1 -> * · inlet 2 (signal scalar)
```

- The second line says whether what plays matches the screen. It can instead
  say the patch was "edited since its last good compile" or that "the last
  compile failed", with the compiler error.
- `selected:` lists up to 12 boxes as id, box text and shape.
- `selected cable:` names each end by its box's operator, not its id, plus the
  outlet or inlet number. If several boxes share that operator, use the
  selected boxes, `look`, or the cables in the source to work out which one is
  meant.

To get to the code:

1. Find the source. On the Code surface, `read_buffer` the code buffer, which
   includes unsaved edits. On the Patch surface, `read_buffer`
   `*patcher-emitted:<path>*` if it is open. That read-only buffer holds the
   source generated from the patch as it stands now. If it is not open, the
   `dsp.lisp` at the path in the context is the last save. When the context
   says "not saved", that file is behind the screen.
2. Find the form. For a box id `x`, look for `(def x …)`, `(param x …)`, an
   `in`/`out` with `@name x`, or `(make-history x)`. For `op#N` and
   `created-N`, use the renaming rules above, or match the box text and its
   inputs.
3. Follow cables by name. A cable into the box is a symbol among its form's
   arguments. A cable out of it is every later form that uses its name.

## Explaining a patch

Walk the signal from the inputs to `out`: for an instrument, `gate`, `pitch`,
`velocity` and `trigger`; for an effect, the left and right inputs. Name each
box by its text (`the svf box`, `phasor rate`), because that is what the user
sees on the canvas. Then say what each stage does to the sound, not only which
operator it calls.

- `dgen_docs` looks up DGenLisp operators and attributes. Use it on any
  operator you are not sure about. `apropos` and `describe` only know
  eseqlisp.
- `dgen_values_live` works out the defs at the knobs as the user has them.
  Pass the code buffer (or the `*patcher-emitted:…*` buffer) and the def
  names. Give host inputs a value in `inputs` (`{"pitch": 220, "gate": 1}`)
  to follow the defs that read them. The knobs come from the track's
  instrument, so for an effect, pass the effect's param values in `inputs`.
  `dgen_values` does the same on a saved file, at the values you give.
- `look` at the patcher buffer shows what the user sees: the layout, which
  cables are tensors, red error boxes and probe readings.
  `view_state_live` on it gives the editor's fields: the selection, shapes,
  error and open macro.
- Feedback (dashed) cables, histories and `delay` are where a patch keeps
  state. Point them out, because they explain ringing, echo and filter
  resonance.

## Changing a patch

`edit_dsp` replaces one top-level DGenLisp form, the one that defines the name
you give (a `def`, `param` or `defmacro`), in the user's open
code buffer. The app then recompiles the preview. Keep each edit to the forms
that need to change, keep names stable, and define every name before the forms
that use it.

What a text edit does to the patch:

- **On the Code surface**, nothing in the sidecar changes when you edit or
  compile. If the user saves code that differs from what the patch generated,
  the item becomes code-authored (`"authored": false`; the positions are kept).
  It then opens on the Code surface until the user switches to Patch and
  saves.
- **Switching back to Patch** after a text edit rebuilds the boxes from the
  code:
  - A box whose id is still a name in the code keeps its position.
  - New forms are placed by the automatic layout, which can put them on top of
    boxes that kept their place.
  - Unnamed nested calls each become their own `op#N` box.
  - Comment boxes are gone.
  - If the code has a form the patch cannot draw (`let`, `if`, `do`,
    `lambda`, `match`, `each`), the switch is refused with
    "Cannot open as patch: …".
  - Switching back with the code unchanged restores the patch exactly.
- **On the Patch surface**, the only code buffer is the read-only
  `*patcher-emitted:…*` view. Ask the user to switch to Code first, or
  describe the change box by box and let them make it. Either way, warn them
  that a code edit costs the patch its comment boxes and puts new boxes in
  automatic positions.

The patch editor also has its own agent bubbles (right-click > Ask Agent…,
or "Connect with Agent…" on a box). These change the patch from inside the
patch editor, and the user stays on the Patch surface. Suggest them when the
user wants to stay in the patch.

Saving is always the user's choice (Cmd+S or the toolbar). A Save from Patch
regenerates `dsp.lisp` from the boxes and rewrites the sidecar. A Save from
Code writes the text as it is.
